Section 01

EHB Umbrella Overview

What is EHB?

EHB (Education Health Business) is a centralized multi-industry trust infrastructure. It does not itself sell products or services — it acts as an umbrella authority that verifies, certifies, and enables 8 specialized sub-platforms operating under its governance.

Every entity operating within any EHB sub-platform — whether a seller listing products, a job seeker posting a profile, or a service provider offering consultancy — must earn an STL (Standard Quality) level from PSS before becoming visible or active on that platform.

STL Levels — Standard Quality Certification

Important: STL levels are assigned per-entity (per product, per business, per service listing), NOT per user account. The same seller can have an SQ10 product and a "not_submitted" product simultaneously.

Level Badge Label Meaning Typical Path Entity Visibility
1 SQ1 — Basic Verified Minimal criteria met: title, description, price, images, category all present Auto-approve (score ≥ threshold) ✓ Visible to buyers
2 SQ2 — Compliance Verified Documentation and compliance fields verified Auto-approve or Franchise review ✓ Visible
3 SQ3 — Financially Verified Financial records and business registration validated Franchise or CRB review ✓ Visible + Trust badge
5 SQ5 — Professional Verified Professional certifications, sector-specific compliance met CRB review (high-stakes sectors) ✓ Premium visibility
7 SQ7 — Expert Verified Expert-level audit passed. Typically requires physical inspection evidence CRB review + Franchise endorsement ✓ Expert badge
10 SQ10 — Elite Certified Highest certification. Full audit trail, all criteria at maximum score CRB full review + Franchise + PSS admin ✓ Elite badge + Promoted

Section 05

Complete STL Flow — 9 Steps

The STL flow is fully event-driven. Each step completes then emits an internal NestJS EventEmitter2 event to trigger the next step. This means the flow is non-blocking and resilient — if a downstream step fails, the STLRequest document preserves state and the flow can resume.

1

Platform Submits Entity for STL

A sub-platform (e.g. GoSellr) calls POST /api/sq/submit on PSS with the entity's data, entity type (product, service, profile), seller ID, and platform ID.

// GoSellr → PSS via PssClientService POST /api/sq/submit { entity_id: "6642f...", entity_type: "product", platform_id: "gosellr", user_id: "seller_abc", entity_data: { title, description, price, category, images, stock, area: "lahore" } }

PSS creates a new STLRequest document with status pending and returns a stl_request_id. GoSellr stores this on the product document.

sq.submitted
2

Entity Classification

PSS's STL Engine classifies the entity based on its entity_type and the submitting platform. This determines which criteria set and rule set to apply.

Classification maps: gosellr + product → criteria_set ID gosellr_product_v1. Different platforms can have different stringency thresholds for the same entity type.

3

Load Criteria Set

The Criteria Service fetches the applicable criteria set from MongoDB. Each criterion has a weight (0–100), a validation rule (type checks, regex, length), and a required flag.

// Example criteria set for gosellr product [ { key: 'title', weight: 15, required: true, rule: 'non_empty' }, { key: 'description', weight: 20, required: true, rule: 'min_length:20' }, { key: 'price', weight: 15, required: true, rule: 'min:1' }, { key: 'images', weight: 25, required: true, rule: 'array_min:1' }, { key: 'category', weight: 15, required: true, rule: 'non_empty' }, { key: 'stock', weight: 10, required: false, rule: 'min:0' }, ]
4

Evaluate Criteria

The Criteria Service runs each criterion against the submitted entity_data. It produces an EvaluationResult — a per-criterion pass/fail breakdown with the total stl_score (0–100%).

Score Formula
sum(passed criteria weights) / sum(all criteria weights) × 100
Required Criterion Failure
Forces score = 0 (auto-reject path)
sq.scored
5

Rule Engine Evaluates Rules

The Rule Engine listens to the sq.scored event. It loads all active rules for the platform, sorts them by priority (ascending, first-match-wins), and tests each rule's condition against the stl_score.

// Rule Engine — evaluateRules() const sortedRules = rules.sort((a, b) => a.priority - b.priority); for (const rule of sortedRules) { if (evaluateCondition(rule.condition, score)) { return rule.action; // first match wins } } return 'reject'; // fallback

7

Review (if routed to Franchise or CRB)

If the rule engine routes to a human review path, the STLRequest document is updated to pending_franchise or pending_edr. A review record is created in the respective collection. A webhook event is pushed to the sub-platform immediately so the seller sees their updated status.

The franchise or CRB reviewer then calls POST /api/franchise/reviews/:id/decision or POST /api/crb/reviews/:id/decision to submit approve/reject/escalate.

franchise.decision / crb.decision sq.decision
8

Assign STL Level & Finalize

When a positive decision is reached (approve path or franchise/CRB approval), PSS's STL Engine calls finalizeApproval(). It maps the score and platform config to the appropriate STL Level (1, 2, 3, 5, 7, or 10) and updates the STLRequest to status approved with the assigned stl_level.

For rejections, finalizeRejection() is called — sets status rejected, records the rejection_reason, and sets can_resubmit: true so the seller can fix and resubmit.

9

Deliver Decision via Webhook

PSS's Webhook Module picks up the sq.decision event. It queues an HMAC-SHA256-signed HTTP POST to the sub-platform's registered callback URL via Bull + Redis.

The sub-platform (e.g. GoSellr) receives the webhook and its webhook handler calls ProductsService.updateSqFromWebhook() to update the product document's stl_status, stl_level, and stl_badge_label.

Fallback: If Redis is down, the webhook cannot be queued. Sellers can click "Refresh Status" to trigger a pull-based sync — GoSellr calls PSS's GET /api/sq/:entityId/status and writes the result back to the local product document.

webhook.delivered / webhook.failed

Section 06

Rule Engine — 4 Routing Paths

Path A: Auto-Approve

≥ 80%

Score meets or exceeds platform threshold. PSS directly assigns STL level and fires webhook. No human review needed. Fastest path — seller sees "Approved" within seconds.

Path B: Franchise Review

60–79%

Score is in the "borderline" range for the area. The submission is forwarded to the area's EHB Franchise holder for manual review. Sub-platform receives pending_franchise status.

Path C: CRB Review

40–59%

Score is too low for franchise but not an outright reject. Escalated to the Ethics Decision Review body for independent oversight. Sub-platform receives pending_edr status.

Path D: Auto-Reject

< 40%

Score is below the minimum threshold, or a required criterion failed (forcing score = 0). Entity is rejected immediately with a rejection_reason. Seller can fix and resubmit.

Rule Priority System

Rules are evaluated in ascending priority order (lower number = higher priority). The first rule that matches wins — no further rules are checked. Platform admins can configure rules per entity type.

Priority Rule Name Condition Action STL Level
1 Elite Auto-Approve score ≥ 95 auto_approve SQ10
2 High Auto-Approve score ≥ 80 auto_approve SQ3–SQ7
3 Franchise Review Band score ≥ 60 franchise TBD by reviewer
4 CRB Review Band score ≥ 40 crb TBD by reviewer
5 Auto-Reject score < 40 reject None

Section 07

Franchise Review Path

1

Rule Engine Routes to Franchise

Score is in 60–79% band. Rule Engine calls forwardToReview('franchise'). PSS emits franchise.review_requested internally.

2

Franchise Record Created

PSS Franchise Service creates a franchise_reviews document. The record includes the entity data, STL score, area identifier (e.g. lahore), and the reviewer's assignment.

Sub-platform receives sq.forwarded_franchise webhook → product status → pending_franchise.

3

Franchise Holder Reviews

The EHB Franchise operator for that area reviews the entity against local standards. They can inspect all submitted entity data including the criteria breakdown.

4

Franchise Submits Decision

Three outcomes available:

  • Approve — assigns STL level, triggers sq.decision (approved) webhook
  • Reject — records reason, triggers sq.decision (rejected) webhook
  • Escalate to CRB — franchise cannot decide → forwarded to CRB
5

Webhook Delivered to Sub-Platform

Bull queue delivers the final decision. Sub-platform updates its local entity status from pending_franchise to approved or rejected.

Auto-Creation of Franchise Records

PSS can automatically create a franchise holder record for a new area when an entity from that area first hits the franchise routing path — if no franchise holder exists yet. This prevents the review from being stuck indefinitely.

Area-Based Routing: The area field submitted with the entity data (e.g. "lahore") determines which franchise holder receives the review. If no franchise holder is registered for that area, PSS queues it under a "default" regional franchise pool.

// Franchise Service — submitDecision() async submitDecision(reviewId, dto) { if (dto.decision === 'approve') { await this.sqEngine.finalizeApproval(request, dto.stl_level); } else if (dto.decision === 'reject') { await this.sqEngine.finalizeRejection(request, dto.reason); } else if (dto.decision === 'escalate') { await this.sqEngine.forwardToReview(request, 'crb'); } }

Section 08

CRB Review & Override Path

What is CRB?

The Central Record Blockchain (CRB) body is an independent oversight layer above both the automated rule engine and franchise reviewers. CRB handles:

Entry Path 1
Rule engine routes score 40–59% directly to CRB
Entry Path 2
Franchise holder escalates a case they cannot decide
Entry Path 3
CRB officer opens a review on any completed decision (override)
CRB Review Flow
1

CRB Record Created

PSS CRB Service handles crb.review_requested event. Creates edr_reviews document. Sub-platform receives sq.forwarded_edr webhook → status pending_edr.

2

CRB Officer Reviews

CRB officers can edit the entity data before deciding — this allows correcting minor data entry issues without forcing a full resubmission. The edit is logged in audit_logs.

3

CRB Submits Decision

Two outcomes: approve (assigns STL level) or reject (records reason). Decision triggers sq.decision event → webhook to sub-platform.

CRB Override Power

Uniquely, CRB officers can override any previously completed decision — even approved entities. This is the highest-authority action in the system.

// CRB Service — submitOverride() async submitOverride(entityId, dto) { // Can reverse an approved product back to rejected // or elevate a rejected entity to approved if (dto.decision === 'revoke') { await this.sqEngine .finalizeRejection(entity, dto.reason); // Webhook fires → GoSellr product goes Approved → Rejected } }

Audit Trail: Every CRB override is written to audit_logs with the officer's ID, timestamp, old value, and new value. This record is immutable.

Webhook Delivery System

Sub-Platform Callback
POST /webhook/pss · Verifies signature · Updates local DB
Push Path (Normal)

When Redis is available, all STL decisions flow via Bull-queued webhooks. The payload is signed with HMAC-SHA256 using a platform-specific secret. The sub-platform must verify the signature before processing.

// Webhook payload shape (PssWebhookPayload) { event: "sq.decision", stl_request_id: "req_abc", entity_id: "6642f...", user_id: "seller_id", platform_id: "gosellr", decision: "approved", // approved | rejected stl_level: 10, decided_by: "rule_engine", // or "franchise" | "crb" decided_at: "2026-04-15T12:00:00Z", rejection_reason: null }
Pull Fallback (Redis Down)

When Redis is unavailable, Bull cannot queue the webhook. In this case the sub-platform's webhook never fires. The Pull Fallback ensures sellers are not stuck permanently:

1

Seller clicks "Refresh Status" in the UI

2

GoSellr calls GET /api/sq/:entityId/status on PSS

3

PSS returns authoritative status from its stl_requests collection

4

syncFromPss() writes the result into GoSellr's products collection — then the UI refetch sees the updated status

Resilience Design: The push (webhook) and pull (refresh-status) paths together guarantee that STL status always converges to the correct value. Redis failure only delays delivery — it never causes permanent data divergence.

Section 11

Architecture Rules — Hard Constraints

What is FORBIDDEN

❌ No direct platform-to-platform communication. GoSellr cannot call OLS's API, and OLS cannot call GoSellr's API. All trust flows through PSS.

❌ No shared MongoDB databases. Each platform has its own MongoDB database/cluster. Cross-database joins are not permitted.

❌ No bypassing PSS verification. A platform cannot mark its own entities as "approved" without a PSS STL decision. The stl_status field on any entity must only be updated via webhook or pull-fallback from PSS.

❌ No user-level STL. STL levels are per-entity, not per-user. A seller account has no STL level — only their submitted entities do.

What is REQUIRED

✓ PSS-First Verification. Every entity that becomes publicly active on any EHB platform must have stl_status = 'approved' set by PSS.

✓ Webhook Signature Verification. All sub-platforms must verify the HMAC-SHA256 signature on incoming PSS webhooks before processing.

✓ Audit Logging. All STL state changes must be written to PSS's immutable audit_logs collection with actor, timestamp, and old/new values.

✓ Pull Fallback Implementation. All sub-platforms must implement the /sq-status pull endpoint that calls PSS and writes back to the local entity document, as a resilience fallback.

NestJS Module Isolation Rules
Module Exports
Only export services that other modules need. Internal helpers stay private.
Event Bus
Internal cross-module communication via EventEmitter2. Never import and call a service from another module directly if an event can serve instead.
PssClientModule
All outbound calls to PSS from a sub-platform go through a shared PssClientService. No module makes raw HTTP calls to PSS independently.

Railway

All NestJS backends (PSS API, GoSellr API, etc.) are deployed as individual Railway services. Each gets its own PORT and environment variables.

Auto-scaling · ENV isolation
Frontends

Vercel

All Next.js frontends deployed on Vercel. Each platform has its own Vercel project with its own domain and environment config pointing to its respective Railway API.

Edge CDN · ISR
Databases

MongoDB Atlas

Each platform has its own MongoDB Atlas cluster or dedicated database. PSS has the pss_db; GoSellr has gosellr_db. No shared collections.

Atlas M0/M10 · TLS

Bull queues for webhook delivery run on Redis. PSS is the only service that uses Redis. Sub-platforms do not need Redis — they only receive webhooks.

EHB Ecosystem — In One Paragraph

EHB is an umbrella trust infrastructure operating 8 specialized sub-platforms across education, health, commerce, employment, and waste management in Pakistan. PSS (Personal Security System) is its central verification engine — every seller, instructor, service provider, or entity on any sub-platform must submit to PSS and earn an STL (Standard Quality) level before going live. PSS evaluates submissions through a 9-step event-driven flow: submit → classify → load criteria → score → rule-engine route → (optional franchise/CRB human review) → assign STL level → webhook delivery. The Rule Engine applies first-match-wins priority rules to route submissions to auto-approve (≥80%), franchise review (60–79%), CRB review (40–59%), or auto-reject (<40%). Decisions are pushed to sub-platforms via HMAC-signed Bull/Redis webhooks, with a pull-based fallback ensuring convergence even when Redis is unavailable. GoSellr is the reference implementation — its PssClientService, ProductsService, and webhook handler demonstrate the integration pattern that all other platforms follow. No platform communicates directly with another — all trust flows through PSS.
